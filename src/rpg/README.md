# 6. RPG 전투 시뮬레이터 ⚔️

> 전사·마법사·궁수 파티 vs 슬라임 군단. 직업마다 다르게 싸우는 캐릭터를 **상속**으로 만들어요.

**난이도** ★★★★☆  **새로 만나는 개념** **상속(extends)**, **추상 클래스**, 오버라이드(@Override), **다형성**, 테스트를 위한 랜덤 고정

```
--- 라운드 1 ---
  미니슬라임의 몸통 박치기! 마법사에게 9 피해
  궁수의 치명타 화살!! 미니슬라임에게 30 피해
  마법사의 파이어볼! 미니슬라임에게 33 피해 (MP 20)
...
=== 결과: 용사 승리! ===
```

---

## 왜 이 프로젝트를 할까?

전사, 마법사, 궁수, 슬라임… 모두 **이름·체력·공격력**이 있고 **맞으면 체력이 깎여요.** 그런데 **공격하는 방식**은 다 달라요.

- 공통인 부분을 클래스마다 복사해서 쓰면? → 피해 계산 규칙을 바꿀 때 4군데를 다 고쳐야 해요. 하나라도 빼먹으면 버그!
- 그래서 **공통 부분은 부모(Character)에 한 번만**, **다른 부분(act)만 자식이** 각자 정해요. 이게 **상속**이에요.

그리고 이 프로젝트의 진짜 하이라이트는 **다형성**이에요.
```java
List<Character> all = [전사, 마법사, 궁수, 슬라임, 킹슬라임]
for (Character c : all) c.act(...);   // 똑같이 act를 불렀는데 각자 자기 방식으로 행동!
```
`Battle`은 상대가 전사인지 슬라임인지 **몰라도** 전투를 진행할 수 있어요. 나중에 "도적"을 추가해도 `Battle`은 한 줄도 안 고쳐도 돼요. 실제 게임·앱 개발에서 **새 기능을 기존 코드를 망가뜨리지 않고 추가하는** 핵심 원리예요.

## 시작 전에: `Slime.java` 읽기 (10분)

`Slime.java`는 상속을 쓰는 법을 보여 주는 **완성된 예시**예요. 세 군데만 보세요.
1. `extends Character` → Character의 필드와 메서드를 전부 물려받아요. (`name`, `hp`, `takeDamage`…)
2. `super(…)` → 부모의 생성자를 불러 공통 필드를 채워요.
3. `@Override String act(…)` → 부모가 "반드시 만들어라"라고 한 `act`를 슬라임 방식으로 만들어요.

Warrior, Mage, Archer도 **같은 모양**이에요. 다른 건 `act` 안의 전략뿐!

---

## 필수 미션

### 작성 1. `takeDamage(power)` — 피해 받기 (부모 클래스)
- **왜 부모에 있을까?** 누가 맞든 피해 계산 규칙은 같으니까요. 여기 한 번 쓰면 모든 캐릭터가 물려받아요.
- **어떻게?** `실제 피해 = power - defense`, 단 최소 1. 체력은 0 아래로 내려가지 않게.
  `Math.max(a, b)` → 둘 중 큰 값. "최소 1"은 `Math.max(1, …)`로 표현할 수 있어요.
- **왜 최소 1일까?** 방어력이 높다고 피해가 0이면 영원히 안 끝나는 전투가 생기니까요. 게임 밸런스 규칙이에요.

### 작성 1-2. `takeTrueDamage(amount)` — 방어 무시 피해
- 방어력을 빼지 않는 버전이에요. 마법사의 파이어볼이 이걸 써요.

### 작성 2. `Warrior.act` — 전사: 3번째마다 강타
- **어떻게?** 행동 횟수 필드(`actionCount`)를 하나 늘리고, 3의 배수인지 `%`로 확인해요.
- **생각해 볼 점:** `actionCount`는 왜 지역 변수가 아니라 **필드**여야 할까요? (act가 끝나면 지역 변수는 사라져요)

### 작성 3. `Mage.act` — 마법사: 마나 관리
- **어떻게?** mp가 충분하면 파이어볼(mp 소모, 방어 무시), 부족하면 지팡이 치기(mp 회복). if-else 하나예요.
- 마법사만 `mp`라는 **자기만의 필드**가 있어요. 자식은 부모에 없는 필드를 더 가질 수 있어요.

### 작성 4. `Archer.act` — 궁수: 확률 치명타
- **어떻게?** `rand.nextInt(100) < 30`이면 30% 확률.
- **왜 `rand`를 밖에서 받을까?** 랜덤이면 테스트할 때마다 결과가 달라서 채점을 못 해요. 그래서 테스트에서는 **항상 같은 값을 내는 가짜 주사위**(`FixedRandom`)를 넣어요. `RpgTest.java`에서 찾아보세요. 실무에서도 이렇게 "바깥에서 넣어 주는" 방식(의존성 주입)으로 테스트를 해요.
- **주의:** `nextInt`를 두 번 부르면 확률이 꼬여요. 한 번 뽑아 변수에 저장하세요.

### 작성 5. `Battle.turnOrder(all)` — 행동 순서
- 살아 있는 캐릭터만 골라 새 리스트에 담고, 속도 높은 순(같으면 이름순)으로 정렬해요.
- 원래 리스트를 정렬하면 팀 구성이 섞여 버려요. **새 리스트**에 담는 이유예요.

### 작성 6. `Battle.pickTarget(enemies)` — 공격 대상 고르기
- 살아 있는 적 중 체력이 가장 낮은 적. "최솟값 찾기" 패턴이에요.
- 체력이 같을 때 **앞에 있는 적**을 고르려면 `<`와 `<=` 중 무엇을 써야 할까요?

### 작성 7. `Battle.isDefeated(team)` — 전멸 확인
- 한 명이라도 살아 있으면 `false`. 지뢰찾기의 `isCleared`와 같은 패턴이에요.

### 작성 8. `Battle.fight(…)` — 전투 진행 ★ 핵심 ★
- 작성 5~7을 조립하는 곳이에요. 주석의 진행 규칙을 순서대로 코드로 옮기세요.
- **여기가 다형성이 일어나는 곳이에요.** `c.act(target, rand)` 한 줄이 전사면 전사답게, 슬라임이면 슬라임답게 움직여요.
- **흔한 버그:** 라운드 순서를 정한 뒤에 **앞 사람에게 맞아 쓰러진** 캐릭터가 공격하는 문제. 차례가 왔을 때 살아 있는지 다시 확인하세요.

## 도전 미션 (직접 설계)

1. **새 직업 만들기**: 성직자(Healer) — 공격 대신 **체력이 가장 낮은 아군**을 회복. 그런데 지금 `act(target, rand)`는 적만 받아요. 구조를 어떻게 바꿔야 할까요? 이 고민이 바로 **설계**예요.
2. **새 몬스터 만들기**: 오크(Orc) — 체력이 절반 이하가 되면 분노해서 공격력 1.5배
3. **전투 통계**: 전투가 끝나면 캐릭터별 총 가한 피해, 받은 피해 순위 출력
4. **밸런스 조정**: `Main`을 100번 돌려 용사 승률을 계산하고, 승률이 50~60%가 되도록 몬스터 능력치 조정하기

## 이 프로젝트에서 AI에게 물어보면 좋은 질문

- "상속을 쓰지 않고 전사·마법사·궁수를 따로 만들면 어떤 문제가 생기는지 예를 들어 설명해 줘."
- "추상 클래스(abstract)는 왜 new로 객체를 만들 수 없어? 만들 수 있다면 어떤 문제가 생겨?"
- "다형성을 게임 말고 **결제 시스템**(카드, 계좌이체, 간편결제) 예시로 설명해 줘."
- "테스트할 때 Random 값을 고정하는 방법들을 알려 줘. 왜 그래야 해?"

**AI 검증 포인트:** AI에게 "도적 클래스 만드는 법"을 물으면 `Battle`까지 고치라는 답이 나올 수 있어요. 정말 `Battle`을 고쳐야 할까요? 다형성을 제대로 이해했다면 고칠 필요가 없다는 걸 알 수 있어요.
